# Доступ к zakupki.gov.ru (ЕИС): проверенный метод

Статус: **проверено на живом сайте** — публичный поиск и карточки закупок отдаются обычным HTTP GET без авторизации, капчи и ЭЦП. Рабочий код: `src/adapters/tender-source/eisTenderSourceAdapter.ts` + `src/adapters/tender-source/eisParser.ts`, демо-запуск: `npm run scrape:eis -- "поставка компьютеров" 6` (результат — `eis-sample.json`, 6 реальных закупок).

## Поиск

```
GET https://zakupki.gov.ru/epz/order/extendedsearch/results.html
  ?searchString=поставка+компьютеров
  &fz44=on&fz223=on&fz615=on
  &priceMin=&priceMax=
  &okpd2=26.20
  &orderBy=UPDATE_DATE&sortDirection=false
  &offset=0
```

Страницы рендерятся серверно (JS не нужен), HTML в UTF-8. Всего в ЕИС > 42 млн записей, выдача по 10 на страницу. **Листать `offset`-ом нельзя**: ЕИС этот параметр игнорирует (проверено 04.10.2026 — `offset=0`, `10`, `20`, `30` вернули одни и те же десять закупок). Настоящие параметры — `pageNumber` и `recordsPerPage` (`_10`, `_20`, `_50`, `_100`, обязательно с подчёркиванием): адаптер берёт нужный размер страницы одним запросом (`recordsPerPageFor` в `eisParser.ts`).

## Селекторы карточки выдачи

| Данные | Селектор / приём |
| --- | --- |
| Карточка | `.search-registry-entry-block` |
| Закон + способ | `.registry-entry__header-top__title` |
| Реестровый номер | `.registry-entry__header-mid__number a` (из `href` также берётся ИНН заказчика для 223-ФЗ) |
| Этап | `.registry-entry__header-mid__title` |
| Объект закупки | `.registry-entry__body-block`, где `.registry-entry__body-title` содержит «Объект закупки» → `.registry-entry__body-value` — брать `.text()` целиком (подсветка поиска бьёт текст на span'ы) |
| Заказчик | тот же блок с заголовком «Заказчик»/«Организация» |
| Цена | `.price-block__value` — содержит неразрывные пробелы (U+00A0, U+2009/202F) и десятичную запятую; парсит `parsePrice` |
| Даты | `.data-block__title` / `.data-block__value` («Размещено», «Обновлено», «Окончание подачи заявок»), формат дд.мм.гггг |

Регион в карточке выдачи **отсутствует** — нужен дозапрос страницы закупки. В правой колонке карточки только «Начальная цена», «Размещено», «Обновлено» и «Окончание подачи заявок» (проверено на живой выдаче 22.09.2026).

## Регион: что проверено и почему фильтр не включён в синхронизацию

Задача «собирать закупки только своего региона» для ЕИС не решается надёжно. Измерения на живом сайте 22.09.2026:

- В серверно отрендеренной форме расширенного поиска регионального поля **нет**: среди `name="…"` присутствуют `customerIdOrg`, `okpd2Ids`, `placingWayList`, `priceFromGeneral`/`priceToGeneral`, даты подачи и размещения — и ни одного поля региона. Есть пустые контейнеры `customerPlaceTagRow` и `oktmoIdsTagRow`, значения в которые подгружает клиентский JS, поэтому состав параметров фильтра из HTML не виден.
- Единственный работающий кандидат — **`oktmoIds`** с кодами ОКТМО субъектов РФ (ОК 033-2013, две цифры региона и шесть нулей). Он действительно географический: `oktmoIds=35000000` даёт аэропорт Симферополь и Бахчисарайский цементный завод, `81000000` — «Аэропорт Байкал (Улан-Удэ)», `76000000` — котельные Карымского, Улётовского и Читинского округов, `45000000` — МОЭК. Несколько кодов перечисляются через запятую.
- Но **полнота непроверяема и непредсказуема**. Из 85 корректных кодов субъектов пять вернули ноль записей при полностью открытой выдаче (Республика Алтай 84000000, Дагестан 82000000, Мордовия 89000000, Хакасия 95000000, Тамбовская область 68000000), а счётчики не соответствуют размеру региона: Крым «более 10 000», Краснодарский край 209, Москва «более 5 900». Флаг `customerPlaceWithNested=on` на результат не влияет. Вложенный код города работает иначе, чем код субъекта: `81701000` (Улан-Удэ) дал «более 6 500» при 629 на всю Бурятию.
- Неизвестные параметры ЕИС молча игнорирует: `regionId`, `districtId`, `customerPlaceIds` не меняют ни счётчик, ни состав выдачи.

Вывод: `oktmoIds` в `buildEisSearchUrl` **не внесён**. Фильтр, который для части регионов молча возвращает пустую ленту, вреднее его отсутствия — пропажу закупок невозможно отличить от того, что их действительно нет. Поле `regions` в `scripts/sync-profiles.json` поэтому применяют только Сбербанк-АСТ и Контур.Закупки, а для ЕИС скрипт печатает предупреждение.

Что нужно, чтобы включить фильтр по ЕИС: выяснить семантику `oktmoIds` (по какому именно реквизиту извещения идёт сопоставление и почему для части субъектов совпадений нет) — например, сняв параметры реального регионального фильтра из запросов клиентского JS в браузере. До этого момента регион в ленте остаётся эвристикой `guessRegion` по тексту заголовка, которая для 113 из 148 живых закупок даёт «Не указан».

### Замер 22.09.2026: почему регион нельзя угадывать по тексту

По дампу живой базы (148 закупок):

| Источник | Всего | `region` заполнен | Определяется по тексту одним кандидатом |
| --- | --- | --- | --- |
| ЕИС | 116 | 3 | 52 |
| Сбербанк-АСТ | 32 | 32 | 26 |

Сбербанк-АСТ регион отдаёт сам, поэтому там поле заполнено всегда. По ЕИС картина иная, и расширять `guessRegion` с 10 регионов до полного списка субъектов плюс столицы **нельзя**, хотя покрытие выросло бы с 3 до ~52 записей:

- текст, по которому пришлось бы угадывать, — это объект закупки, адрес поставки и наименование заказчика вместе. Совпадение чаще всего даёт именно заказчик, то есть определяется его штаб-квартира, а не место работ. «Устройство дорожной разметки на объекте „Реконструкция а/д г. Жуковский ул. Туполева“» таким способом уезжает в Москву, хотя работы в Московской области;
- у 8 из 148 закупок находится два и более кандидата сразу (Москва + Республика Коми, Омская + Томская), и выбрать между ними нечем;
- неверно присвоенный регион хуже «Не указан»: региональный фильтр в приложении такую закупку молча спрячет, а пустой фильтр пользователь отличит от отсутствия закупок хотя бы по счётчику.

Рабочий путь — дозагрузка карточки закупки, где место поставки указано явно (см. «Страницы закупки» и ROADMAP, Этап 2).

## Страницы закупки

- 44-ФЗ: `/epz/order/notice/{zk20|ea20|ok20}/view/common-info.html?regNumber=...`
- Печатная форма 44-ФЗ (проверена: 56 КБ, поля «Объект закупки», «НМЦК», «Заказчик», «Способ определения», «Обеспечение заявки»): `/epz/order/notice/printForm/view.html?regNumber=...`
- 223-ФЗ: `/223/purchase/public/purchase/info/common-info.html?regNumber=...`
- Организация 44-ФЗ: `/epz/organization/view/info.html?organizationCode=...`
- Организация 223-ФЗ: `/epz/organization/view223/info.html?inn=&kpp=&ogrn=`

## Надёжность и ограничения

- Rate limit: эмпирически безопасно ~3 запроса/сек — в адаптере throttle.
- Varnish иногда отвечает пустым телом — retry с экспоненциальным backoff (в адаптере).
- Разное TTL кэша: лента ~5 минут, карточка контракта ~сутки.
- Вёрстка меняется без предупреждения — парсер ломается молча; нужны тесты-фикстуры HTML и мониторинг пустых результатов.
- Один ИНН может встречаться в трёх форматах (ИНН, organizationId, organizationCode).
- Юридически парсинг — серая зона (условия использования сайта); официальный SOAP API (int44.zakupki.gov.ru) требует квалифицированную ЭЦП юрлица — это барьер для прототипа.

## Sandbox-особенность (только локальная отладка)

В окружении с MITM-прокси Node fetch падает с `SELF_SIGNED_CERT_IN_CHAIN`, хотя curl работает (системный CA). Для разовых демо-запусков допустимо `NODE_TLS_REJECT_UNAUTHORIZED=0` **на уровне команды**:

```bash
NODE_TLS_REJECT_UNAUTHORIZED=0 npm run scrape:eis -- "поставка компьютеров" 6
```

В коде адаптера отключение проверки сертификата не используется и не должно использоваться в продакшене.

## Проверка кодировки

Консоль Windows может отображать кириллицу как `??` — это ограничение вывода терминала, а не данных. Корректность UTF-8 проверяется кодами символов (например, 0x41e 0x43f для «Оп»), а не глазами.
