# Поисковый слой на нескольких площадках: реестр источников и ТЭК-Торг

Дата: 2026-10-01. Статус: проект, ждёт решения владельца.

## Проблема

Владелец собирается уходить от Контур.Закупок и собирать лоты с площадок напрямую, вместе
с документацией. Зонды одиннадцати площадок (`docs/REFERENCE_PLATFORM_PROBES.md`) показали,
что источников не десять, а четыре: ЕИС, Сбербанк-АСТ, Контур и ТЭК-Торг. Остальные либо
зеркалят ЕИС с закрытым файл-хостом, либо отдают список только внутренним API со
статическим токеном из JS-бандла, либо закрыты антиботом. Обходить защиту площадки мы не
будем: это не тот фундамент, на котором строят продукт для партнёра.

Сегодняшний код к четырём источникам не готов, и дело не в числе. Один источник
размазан примерно по десяти местам:

- `scripts/sync-eis.ts:101` — `SYNC_SOURCES`, `DEFAULT_SOURCES`;
- `scripts/sync-eis.ts:234` — `profileSources` возвращает три отдельных буля
  `wantEis` / `wantSber` / `wantKontur`;
- `scripts/sync-eis.ts:504-518` — три адаптера создаются подряд в теле прогона;
- `scripts/sync-eis.ts:176` — `probeSources`, `:532` — `perSource` для безопасной очистки;
- `src/repositories/tenderRepository.ts:89` — `TENDER_SOURCE_PRIORITY`;
- `src/domain/deepAnalysis.ts:183` — `DOCUMENTATION_SOURCES`, `:188` — `SOURCE_REASONS`;
- `src/services/tenderDocumentsFetcher.ts:182` — `documentationUnavailableReason` со своим
  `switch` по тем же источникам;
- `supabase/migrations/` — CHECK-ограничение `tenders_data_source_check`, которое каждый
  новый источник правит отдельной миграцией.

Четвёртый источник — это правка во всех десяти местах, пятый — тоже. При этом факт «умеет
ли источник отдавать документацию» записан дважды и в двух слоях: списком
`DOCUMENTATION_SOURCES` с текстами `SOURCE_REASONS` в домене и `switch`-ем
`documentationUnavailableReason` в сервисе. Расходятся они молча: компилятор не знает, что
`switch` обязан совпадать со списком, и у источника, который документацию отдаёт, причина
отказа всё равно найдётся — просто её никто не увидит.

Сроки поджимают отдельно: подписка Контур.Закупок, проверенная живым вызовом
`GET /api/kontur/usage` 01.10.2026, продлена до **2026-10-03T18:59Z (21:59 МСК 03.10.2026)**.
Продлевают её, судя по датам, короткими отрезками. Кнопка «Найти новые закупки» и платная
карточка работают только на этом ключе.

## Что проверено и на что можно опираться

**ТЭК-Торг** — единственная площадка с официальным публичным экспортом, и 01.10.2026 он
проверен живым вызовом (тринадцать запросов, детали в `docs/REFERENCE_TEK_TORG_API.md`):

- SOAP-операция `procedures` на `https://api.tektorg.ru/procedures/soap`, ключа не требует
  ни схема, ни практика;
- секция `zakupki` («223-ФЗ и Коммерческие закупки») — 136 254 процедуры, за сутки
  01.10.2026 — 73 новых;
- `startUpdateAt`/`endUpdateAt` — настоящая дельта: 207 процедур за сутки, из них закупки,
  опубликованные 23–24.09, у которых изменилось только состояние. Это готовый вход для
  `checkChanges`;
- `limitPage=500` принят: 500 процедур одним ответом, 4,7 МБ, 20,3 с. Суточная дельта
  помещается в один запрос;
- из 73 процедур за сутки у 47 заполнен `eisRegistryNumber` — они и так видны в ЕИС, а
  **26 без номера ЕИС — чисто коммерческие, которых в ЕИС нет**. Это и есть прирост;
- документы отдаёт байтами: `<file>` содержит адрес
  `https://api.tektorg.ru/open-api/documents/procedure/{id}`, HEAD на который отвечает
  `200`, `Content-Type: application/msword`, `Content-Length: 44544`, `Accept-Ranges: bytes`,
  ranged GET — `206 Partial Content`, первые байты `D0 CF 11 E0` (настоящий OLE2-`.doc`).
  Ключа на этом хосте тоже нет.

**Контур.Закупок** — работает, 9 из 30 поисков потрачено 01.10, `tariffError: null`,
подписка до 03.10.2026. Документацию отдаёт только платной карточкой.

**Сбербанк-АСТ** — поисковый API бесплатный и robots-чистый, документов не отдаёт вовсе:
файлы в карточке за входом по КЭП.

**ЕИС** — хребет, уже в проде: списки, карточки, вложения. Регионального фильтра в выдаче
нет (`docs/ACCESS_EIS.md`).

## Решение

### 1. Каталог источников — один факт в одном месте

Факты об источнике, которые нужны домену и репозиторию, собираются в одну таблицу
`src/domain/sources.ts`. Домен не импортирует ничего сверху, поэтому конструкторов
адаптеров здесь нет — только данные:

```ts
export interface SourceFacts {
  readonly source: TenderDataSource;
  /** Как источник назван в интерфейсе. */
  readonly title: string;
  /** Платный источник опрашивается по своему правилу, бесплатный — каждый прогон. */
  readonly cost: "free" | "paid";
  /** Отдаёт ли источник байты документов. */
  readonly documents: "bytes" | "none";
  /** Приоритет в upsertByRegNumber: чья запись останется, если закупку принесли двое. */
  readonly priority: number;
  /** Входит ли в прогон по умолчанию, когда профиль не указал sources. */
  readonly byDefault: boolean;
  /** Почему документов нет; null, когда они есть. */
  readonly documentsReason: string | null;
}

export const SOURCES: readonly SourceFacts[];
```

Из неё выводятся все четыре нынешних разрозненных списка. `TENDER_SOURCE_PRIORITY`
становится `Object.fromEntries(SOURCES.map(...))`, `DOCUMENTATION_SOURCES` —
фильтром по `documents === "bytes"`, `SOURCE_REASONS` и `documentationUnavailableReason` —
чтением `documentsReason`. Три копии одного факта превращаются в одну.

Конструкторы и проверки доступности живут в своём слое — `src/adapters/tender-source/registry.ts`:

```ts
export interface SourceBinding {
  readonly source: TenderDataSource;
  /** Жив ли источник прямо сейчас: прогон не должен падать из-за одного хоста. */
  probe(): Promise<boolean>;
  /** Создать адаптер. Возвращает null, когда источник не настроен (нет ключа). */
  create(): Promise<TenderSourceAdapter | null>;
  /** Как часто опрашивать: null — каждый прогон. */
  readonly cadenceHours: number | null;
}

export const SOURCE_BINDINGS: readonly SourceBinding[];
```

Две таблицы связаны одним тестом: множество `source` в `SOURCES` и в `SOURCE_BINDINGS`
совпадает и покрывает `TenderDataSource` целиком. Тест — единственная защита от того,
что новый источник добавили в домен и забыли в адаптерах; компилятор по union-типу это
не поймает, потому что массивы не исчерпывающие.

`profileSources` после этого возвращает не три буля, а список источников, и тело прогона
идёт циклом по нему. Новое место, которое нужно править при добавлении площадки, — одно.

### 2. ТЭК-Торг: адаптер, парсер, маппер

Три файла, каждый со своей ответственностью:

- `src/adapters/tender-source/tektorgSoap.ts` — конверт запроса и разбор ответа.
  XML разбираем существующим `src/lib/fsnb/xmlTokenizer.ts` (`XmlToken`,
  `parseXmlAttributes`, `decodeXmlEntities`): он уже написан, протестирован и не тянет
  зависимость. Нового XML-парсера в проекте не будет.
- `src/adapters/tender-source/tektorgMapper.ts` — процедура площадки в нашу `Tender`.
- `src/adapters/tender-source/tektorgTenderSourceAdapter.ts` — реализация порта
  `TenderSourceAdapter` поверх первых двух.

Правила маппера, каждое проверяется тестом:

**Ключ дедупликации.** `upsertByRegNumber` ищет по `reg_number` по всей таблице, поэтому
номер обязан быть глобально однозначным. Если `eisRegistryNumber` непуст — `reg_number`
равен ему, и запись схлопывается с еисовской (приоритет ЕИС 50 выше, так что данные ЕИС
и останутся). Если пуст — `reg_number` получает префикс `TEKTORG-` плюс `registryNumber`
площадки: «ЗП610110» не похож на номер ЕИС, но полагаться на это нельзя. В `external_id`
пишется `registryNumber` площадки — по нему работает покупка карточки и поиск одной закупки.

**Закон.** Секция `44fz` → `FZ_44`. Секция `zakupki` → `FZ_223`, если `eisRegistryNumber`
заполнен, и `COMMERCIAL`, если пуст. Тот же признак, что и в дедупликации: попадание в ЕИС
означает 223-ФЗ.

**Способ размещения.** Восемь типов процедур секции `zakupki` ложатся так: Аукцион и
Аукцион в двух частях → `ELECTRONIC_AUCTION`, Конкурс → `OPEN_CONTEST`, Запрос
предложений → `REQUEST_FOR_PROPOSALS`, Запрос цен и Запрос котировок →
`REQUEST_FOR_QUOTATION`, Закупка у единственного поставщика → `SOLE_SUPPLIER`,
Предварительный отбор → `OTHER`. Неизвестный `typeId` → `OTHER`, а не ошибка: словарь из
87 типов площадка может пополнить, и прогон из-за этого вставать не должен.

**Цена.** У 58 лотов из 74 `startPrice` заполнен, у 16 элемента нет вообще,
`startPriceUndefined` площадка не присылает. Правило: лот один и цена есть — берём её;
лотов несколько и цена есть у всех — берём сумму; хотя бы у одного цены нет — `price: null`,
и лента показывает «цена не указана» (поведение уже реализовано, задача #98). Придумывать
цену по одному лоту из пяти нельзя: это занижение в разы, и оно влияет на вердикт.
Валюта — `currency` площадки, в проверенном ответе у всех 73 RUB.

**Предмет.** `title` процедуры; `subject` каждого лота уходит в `lots`. У 8 лотов из 74
`subject` пуст — такие лоты остаются в списке пустыми, а не заменяются названием процедуры.

**Заказчик и регион.** `organizer.fullName` и `organizer.inn`; регион —
`organizer.address.region`, при пустом — `region` первого заказчика из `customers`.

**Документы.** `fetchDocuments` возвращает по одному `TenderDocument` на каждый `<file>`
процедуры и её лотов: `url` — адрес из `<file>`, `fileName` — из `<filename>` ответа,
`type` — `NOTICE` для документа процедуры и `ATTACHMENT` для документов лота. Байты по
этому адресу отдаются без ключа, значит скачивать их будет воркер на российском сервере
через ту же очередь `sync_jobs` и тот же `attachmentParser` — нового конвейера
документации не нужно. Элемент `<removed>` вместо `<file>` документом не становится: это
отозванный файл, и он попадает в `skippedDocuments` с причиной «документ отозван
площадкой». Именно такого сигнала ЕИС нам не даёт.

**Поиск по словам.** Площадка не умеет искать по ключевым словам и регионам — в запросе
нет таких параметров, есть только даты, секция, номера, `typeId` и ИНН. Поэтому отбор
наш: прогон забирает суточную дельту целиком (207 процедур, один запрос) и пропускает её
через тот же `textSearch`, которым лента ищет по сохранённым данным. Это дешевле, чем
кажется: 207 записей против 30, которые Контур отдаёт за один платный поиск, и бесплатно.
ИНН заказчиков при этом push-ится в запрос площадки (`customerINN`) — единственная фильтрация,
которую она умеет.

### 3. Миграция и регистрация

`supabase/migrations/20261001000006_add_tek_torg_source.sql` — по образцу
`20260921000003_add_kontur_source.sql`: снять `tenders_data_source_check`, добавить заново
со значением `TEK_TORG`. Применяется через SQL Editor (CLI в этом проекте не работает).
До применения адаптер не пишет ничего: `SOURCES` держит `byDefault: false` для `TEK_TORG`,
и источник включается только явным `--sources=TEK_TORG`.

`TEK_TORG` добавляется в union `TenderDataSource` (`src/types/database.ts:200`) сразу —
иначе маппер не соберётся. Записей с таким значением в базе не появится, пока миграция не
применена, поэтому порядок безопасный: код впереди, данные после.

### 4. Документация и глубокий анализ

После первого успешного прогона `documents: "bytes"` у `TEK_TORG` делает его участником
`DOCUMENTATION_SOURCES`, и карточка закупки получает кнопку глубокого разбора. Причина
`documentsReason` на это время — «ТЭК-Торг: источник подключается, документация ещё не
загружается». Текст показывается в карточке, как у Сбербанк-АСТ, и не даёт пустого
ожидания.

Суточный лимит разборов (20, `src/domain/analysisQuota.ts`) не меняется: ТЭК-Торг
увеличивает число закупок с читаемой документацией, но не число разборов, которые
владелец готов оплатить.

## Чего решение не делает

- Не отключает Контур. После 03.10.2026 он отключится сам, если подписку не продлят;
  код к этому готов тем, что источник платный и его отсутствие — штатная ветка
  `create(): null`.
- Не забирает все 136 254 процедуры секции. Полный перебор — это 273 страницы по 20 с,
  порядка полутора часов, и он нужен только если владелец решит искать по всей секции,
  а не по профилям. Первая волна — суточная дельта.
- Не трогает клиентский поиск. Лента по-прежнему ранжирует то, что пришло из
  `/api/tenders` (до 1000 строк). Серверный полнотекст — отдельная задача #99, и она
  понадобится, когда строк станет больше нескольких тысяч.
- Не идёт на площадки, закрытые антиботом или внутренним API.

## Порядок работ

1. Каталог источников и реестр привязок; `profileSources`, `TENDER_SOURCE_PRIORITY`,
   `DOCUMENTATION_SOURCES`, `SOURCE_REASONS`, `documentationUnavailableReason` — выводы
   из него. Поведение не меняется, доказательство — существующие тесты плюс тест
   покрытия двух таблиц.
2. `tektorgSoap.ts`: конверт и разбор ответа, фикстура — две процедуры из живого ответа
   (обрезанная, без личных данных сверх того, что площадка публикует сама).
3. `tektorgMapper.ts`: правила дедупликации, закона, цены, предмета, региона — каждое
   отдельным тестом.
4. Адаптер и привязка в реестре; `--sources=TEK_TORG --dry-run` на живом API.
5. Миграция в SQL Editor, первый настоящий прогон суточной дельты, сверка 26 коммерческих
   закупок с лентой.
6. Документы через очередь воркера, включение в `DOCUMENTATION_SOURCES`, первый глубокий
   разбор закупки, которой нет в ЕИС.

Шаги 1–4 не трогают прод и не требуют ключей. Шаг 5 — первая запись в базу, шаг 6 — первый
платный разбор.

## Проверка

- `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` — зелёные до и после;
  шаг 1 не имеет права изменить ни одного существующего ожидания.
- Тест покрытия: `SOURCES`, `SOURCE_BINDINGS` и `TenderDataSource` описывают одно и то же
  множество источников.
- Тесты маппера на живых значениях из ответа за 01.10.2026: «ЗП610110» с `eisRegistryNumber`
  32616430599 → `reg_number` 32616430599, закон `FZ_223`; «ЗП610102» без номера ЕИС →
  `reg_number` `TEKTORG-ЗП610102`, закон `COMMERCIAL`; лот без `startPrice` → `price: null`.
- Прогон `--dry-run` печатает, сколько процедур пришло, сколько отсеяно профилем, сколько
  совпало с ЕИС по номеру, и не пишет в базу.
- Первый настоящий прогон: в ленте появляются закупки с `data_source: TEK_TORG`, у каждой
  есть предмет и хотя бы один документ, у закупки без номера ЕИС кнопка глубокого разбора
  активна.

## Открытые вопросы к владельцу

1. Продлевать ли Контур после 03.10.2026. Если нет — кнопка «Найти новые закупки»
   остаётся без платного источника, и живой поиск по требованию даёт только ТЭК-Торг
   (бесплатно, но без фильтра по словам на стороне площадки).
2. Какие секции ТЭК-Торга брать. По профилю клиента (строительный подрядчик с СРО)
   осмысленны РЖД, Транснефть, Интер РАО, Норникель, ИНК, Мосэнерго, ЕвроСибЭнерго.
   Вся секция `zakupki` — это 207 процедур в сутки до отбора профилем.
3. Нужен ли полный перебор 136 254 процедур один раз (полтора часа, ~1,3 ГБ ответов),
   чтобы искать и по уже идущим закупкам, или начинаем с дельты и копим историю с нуля.
