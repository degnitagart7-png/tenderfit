# Сервер в России: воркер, очередь заданий и обслуживание

Документ для того, кто ставит и обслуживает воркер. О самом коде — комментарии
в `scripts/worker.ts` и `src/domain/workerSchedule.ts`; здесь — порядок действий
и то, что считать нормой, а что поломкой.

## Зачем нужен отдельный сервер

Прод живёт на Vercel, то есть за рубежом. ЕИС и её хранилище файлов оттуда не
отвечают: 24.09.2026 запрос из Амстердама оборвался без ответа (код 000), а из
Одинцова те же семь файлов пришли за 6,7 секунды. Часть коммерческих площадок
зарубежные адреса закрывает так же. Поэтому плановый обход источников и
скачивание документации обязаны выполняться с российского адреса, и кнопка
«Найти новые закупки» на дашборде не опрашивает площадки из браузера, а ставит
задание в очередь этого сервера.

Из-за рубежа отвечают платные агрегаторы — Контур.Закупки, например. На них
приложение не опирается: это необязательный источник, отказ которого прогон
печатает причиной и продолжает работу остальными площадками
(`docs/REFERENCE_KONTUR_API.md`).

До переезда этим занимался домашний ПК по расписанию Windows Task Scheduler
(задача «TenderFit EIS Sync», `scripts/sync-eis.bat`, минута :54 каждые два часа).
Арендованный сервер заменяет его и добавляет очередь: прогон по кнопке на
дашборде не ждёт ближайшего раза по расписанию, а документация закупок
догружается отдельным заданием, а не следующим прогоном.

## Что делает воркер

Один тик (по умолчанию раз в минуту):

1. определяет адрес выхода в сеть и пишет пульс в `worker_heartbeat`;
2. возвращает в очередь задания, зависшие в `processing` после перезагрузки;
3. просит у домена решение — плановый прогон, задание из очереди или ничего;
4. выполняет **одно** действие и записывает исход.

Одно действие на тик намеренно: плановый прогон занимает минуты и может
растянуться до ~45 минут, а параллельная загрузка документации качала бы те же
вложения дважды.

Приоритет решений (`planTick`, правила покрыты тестами):

| Условие | Действие |
| --- | --- |
| этот сервер ещё ни разу не делал плановый прогон | прогон сразу |
| прогон просрочен вдвое (4 ч при интервале 2 ч) | прогон, очередь больше не удерживает расписание |
| в очереди есть задание | задание — его поставил человек |
| подошёл срок прогона | прогон |
| иначе | ничего, «делать нечего» в журнале раз в 15 минут |

Задания трёх видов:

| Вид | Что делает | Кто ставит |
| --- | --- | --- |
| `full_sync` | прогон целиком: все источники профилей и догрузка документации по закупкам из «Интересного» | расписание сервера и кнопка «Найти новые закупки» на дашборде |
| `documents` | документация по перечисленным номерам | сервер, а не браузер: `POST /api/kontur/sync` после платного поиска и покупка платной карточки |
| `estimate` | расчёт сметы по документации закупки | `POST /api/estimate` |

Что воркер **не** делает: не запускает глубокий разбор по заданию `documents`.
Разбор стоит ≈6 ₽ за закупку при потолке 20 в сутки, а платный поиск приносит
десятки номеров — оплачивать их без решения партнёра нельзя. Разбор добирают
закупки, переведённые в «Интересное», и купленная карточка: задачу разбора
создаёт прод, а не очередь.

## Требования к серверу

- Linux с systemd и российским адресом (проверка ниже обязательна до установки);
- Node.js 20 LTS или новее — Next.js 14 требует не ниже 18.17, типы в проекте
  от `@types/node` 20;
- **npm 10 или новее**: `package-lock.json` версии 3 собран npm 11, и npm 9 из
  apt Ubuntu отвечает на `npm ci` ошибкой «Missing: @emnapi/core from lock file».
  Это не порча lock-файла, а старый npm: лечится `npm install -g npm@11`.
  `deploy/deploy-worker.sh` проверяет версию до отправки архива;
- корневой сертификат Минцифры в системном хранилище — без него ЕИС не открывается
  ни с какого адреса (раздел «Корень Минцифры» ниже);
- доступ наружу по 443 к `zakupki.gov.ru` и её хранилищу файлов,
  `www.sberbank-ast.ru`, `api-zakupki.kontur.ru`, `*.supabase.co` (Стокгольм),
  хосту прода (`SYNC_BASE_URL`, по умолчанию `tenderfit-ai-sage.vercel.app`) и
  одному из сервисов определения адреса — `ipinfo.io`, `ipapi.co`,
  `api.ipify.org`, `ifconfig.me`. К `routerai.ru` сервер не обращается: глубокий
  разбор выполняет прод, а воркер лишь зовёт `${SYNC_BASE_URL}/api/analysis/worker`;
- память: документация разбирается в процессе и отдельный файл может весить
  до 50 МБ, поэтому 2 ГБ — разумный минимум. Это оценка по размеру файлов,
  а не замер под нагрузкой. На поставленном сервере 4 ГБ и 2 ядра, и пробный
  запуск воркера занял меньше секунды до первого обращения к базе;
- диск: кода и зависимостей около 1 ГБ (по факту установки 25.09.2026 —
  680 пакетов, 23 с на `npm ci`). Файлы на диске сервера не задерживаются —
  извлечённый текст пишется в таблицу `tender_documents`, поэтому место нужно
  только под журнал и замок воркера.

## Корень Минцифры: без него ЕИС не открывается

Первое, что ломается на новом сервере, — не география, а TLS. `zakupki.gov.ru`
отдаёт сертификат, подписанный **Russian Trusted Root CA** (Минцифры), которого
нет в наборе Mozilla:

```text
0 s:CN=*.zakupki.gov.ru, O=ФЕДЕРАЛЬНОЕ КАЗНАЧЕЙСТВО, C=RU
  i:C=RU, O=The Ministry of Digital Development and Communications, CN=Russian Trusted Sub CA
1 s:CN=Russian Trusted Sub CA   i:CN=Russian Trusted Root CA
2 s:CN=Russian Trusted Root CA  i:CN=Russian Trusted Root CA
```

Без этого корня `curl` отвечает `SSL certificate … self-signed certificate in
certificate chain`, а код — `000`. **Это не блокировка адреса**, и лечится она
не отключением проверки, а установкой сертификата:

```bash
# отпечаток SHA-256 того корня, который проект считает настоящим
D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31
```

Файл лежит в дереве проекта — `deploy/certs/russian_trusted_root_ca.pem`, —
и `deploy/deploy-worker.sh` ставит его в `/etc/tenderfit/` и в
`/usr/local/share/ca-certificates/`, предварительно сверив отпечаток: не
совпал — деплой прерывается, чужой корень в доверие не добавляется.

Откуда взялась уверенность, что корень настоящий. Официальный портал
`guca.gov.ru` с сервера не разрешился по DNS, поэтому сертификат сверялся
другим способом: ту же цепочку с тем же отпечатком отдаёт `sberbank.ru` —
оператор, не связанный ни с Казначейством, ни с хостером. Совпадение ключа у
двух независимых организаций и есть проверка. Рядом для контраста:
`mos.ru` и `nalog.gov.ru` отвечают обычными GlobalSign и ISRG, то есть
провайдер трафик не подменяет — иначе иностранные корни выглядели бы так же.

Ubuntu собирает Node с системным хранилищем сертификатов, поэтому после
`update-ca-certificates` корень подхватывается сам. Переменная
`NODE_EXTRA_CA_CERTS=/etc/tenderfit/russian_trusted_root_ca.pem` в окружении
воркера оставлена намеренно: она страховка на случай Node из другого источника
(например NodeSource), который читает только свой встроенный набор.

## Проверка до установки

Выполнять **с нового адреса**, без `NODE_TLS_REJECT_UNAUTHORIZED` и без VPN:

```bash
UA='Mozilla/5.0 (X11; Linux x86_64) TenderFit/1.0'
curl -sS -A "$UA" -o /dev/null -w 'ЕИС главная: %{http_code}\n' --max-time 20 https://zakupki.gov.ru/
curl -sS -A "$UA" -o /dev/null -w 'ЕИС карточка: %{http_code} %{size_download} байт\n' --max-time 20 \
  'https://zakupki.gov.ru/epz/order/notice/ea44/view/common-info.html?regNumber=0301300335621000492'
curl -sS -o /dev/null -w 'хранилище 44-ФЗ: %{http_code}\n' --max-time 20 \
  'https://zakupki.gov.ru/44fz/filestore/public/1.0/download/priz/file.html'
curl -sS -o /dev/null -w 'Контур: %{http_code}\n' --max-time 20 https://api-zakupki.kontur.ru/
curl -sS -o /dev/null -w 'Supabase: %{http_code}\n' --max-time 20 "$SUPABASE_URL/rest/v1/"
curl -sS --max-time 15 https://ipinfo.io/json   # страна выхода обязана быть RU
```

Как читать:

- ЕИС и её хранилище обязаны ответить чем угодно, кроме `000`. Код 400, 404 или
  500 на запросе без параметров означает, что адрес пускают; `000` — обрыв
  соединения, и с таким адресом ставить воркер бессмысленно.
- `000` вместе с текстом `self-signed certificate in certificate chain` — это
  **не блокировка**, а отсутствующий корень Минцифры: раздел выше.
- `404` на `https://zakupki.gov.ru/` без `User-Agent` — норма: корень сайта
  отдаёт пустую страницу curl. С браузерным `User-Agent` тот же адрес отвечает
  `301` на `/epz/main/public/home.html`. Поэтому в команде выше заголовок есть.
- Настоящий признак того, что ЕИС доступна, — карточка закупки: `200` и сотни
  килобайт HTML. Замер 25.09.2026 с сервера в Петербурге: `200`, 188 355 байт
  за 0,37 с; выдача расширенного поиска — `200`, 255 935 байт.
- `000` у Контур — блокер для платного источника, но не для ЕИС.

Отдельно убедитесь, что выход действительно российский: воркер определяет его сам
через `ipinfo.io` и пишет в пульс, но узнать заранее дешевле, чем разбирать
подпись «Сервер выходит в сеть не из России» на панели. Тот же замер дал
`"city": "Saint Petersburg", "country": "RU", "org": "AS198610 Beget LLC"`, и
воркер при пробном запуске напечатал `выход в сеть: 5.35.86.186 (RU)`.

## Установка

Порядок ниже — тот, которым сервер 5.35.86.186 (Ubuntu 26.04, 2 ядра, 4 ГБ)
был поставлен 25.09.2026. Шаги 1–4 и 6 выполняются на сервере, шаг 5 — с рабочей
машины.

```bash
# 1. Node и npm. В apt Ubuntu 26.04 лежит Node 22 с npm 9 — npm обновляется
#    отдельно, иначе npm ci падает на lock-файле версии 3.
sudo apt-get update && sudo apt-get install -y nodejs npm
sudo npm install -g npm@11
node -v && npm -v            # нужно: node ≥ 20, npm ≥ 10

# 2. Пользователь и папки. Отдельный пользователь нужен, чтобы компрометация
#    воркера не давала прав на всю машину.
sudo useradd --system --create-home --shell /usr/sbin/nologin tenderfit
sudo install -d -o tenderfit -g tenderfit /opt/tenderfit-ai
sudo install -d -o tenderfit -g tenderfit /opt/tenderfit-ai/logs
sudo install -d -m 750 -o root -g tenderfit /etc/tenderfit

# 3. Окружение: ключи живут здесь, а не в дереве кода.
sudo cp deploy/worker.env.example /etc/tenderfit/worker.env
sudo chown root:tenderfit /etc/tenderfit/worker.env
sudo chmod 640 /etc/tenderfit/worker.env
sudo nano /etc/tenderfit/worker.env

# 4. Служба.
sudo cp deploy/tenderfit-worker.service /etc/systemd/system/
sudo systemctl daemon-reload

# 5. Код, зависимости и корень Минцифры. С рабочей машины, из корня проекта:
TENDERFIT_VPS=root@<адрес> \
TENDERFIT_SSH_KEY=~/.ssh/<ключ сервера> \
  deploy/deploy-worker.sh

# 6. Включить и запустить.
sudo systemctl enable --now tenderfit-worker
journalctl -u tenderfit-worker -f
```

Пользователь в `TENDERFIT_VPS` — тот, кто входит по ssh и пишет в `/opt` и
`/etc/tenderfit`: root или пользователь с `sudo -n`. Служебный `tenderfit` не
годится — он создан с оболочкой `nologin` и по ssh не входит. После распаковки
скрипт сам передаёт дерево пользователю `tenderfit`, от которого работает служба.

Пути в юните (`WorkingDirectory`, `ExecStart`, `ReadWritePaths`) и пользователя
(`User`, `Group`) правят под свою установку: systemd не подставляет переменные
в эти поля из окружения.

Что делает `deploy/deploy-worker.sh` и чего от него ждать:

- собирает архив дерева **без** `node_modules`, `.next`, `logs` и любых `.env*`
  и проверяет оглавление до отправки — попавший в архив файл окружения обрывает
  деплой, потому что уехавший на чужой сервер ключ считается засвеченным;
- сверяет отпечаток `deploy/certs/russian_trusted_root_ca.pem` с зашитым
  значением и только потом кладёт его в `/etc/tenderfit/` и в системное
  хранилище;
- запускает полный `npm ci` (не `--omit=dev`): воркер работает через tsx, а tsx
  лежит в devDependencies;
- печатает дату `scripts/worker.ts` — ровно то, что видно на панели в плитке
  «Код на сервере»;
- без флага `--restart` службу не трогает: перезапуск прерывает текущее задание,
  и решать, сейчас ли это уместно, должен человек.

Миграция очереди должна быть применена **до** первого запуска —
`supabase/migrations/20260925000004_add_sync_jobs.sql` в SQL Editor проекта
Supabase (CLI к этому проекту не подключается, а по REST DDL не выполняется:
ключ роли service даёт доступ к данным, но не к схеме). Без неё воркер пишет
в журнал `Could not find the table 'public.worker_heartbeat' … (PGRST205)`
и выходит, а панель показывает «Состояние сервера не прочитано».

Проверить, применена ли миграция, можно без браузера — анонимный ответ `200`
означает, что таблица есть, `404` с кодом `PGRST205` — что её нет:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" \
  -H 'Range: 0-0' "$SUPABASE_URL/rest/v1/sync_jobs?select=*"
```

Переменная `SYNC_WORKER_ID` на Vercel **не нужна**: значение `ru-vps` совпадает
с `DEFAULT_WORKER_ID` в `src/domain/workerStatus.ts`, и прод читает пульс по
нему же. Если имя в `/etc/tenderfit/worker.env` меняют, переменную на Vercel
придётся завести — иначе панель вечно показывает «ещё не выходил на связь».

## Первый прогон и что считать успехом

На первом тике сервер видит, что планового прогона у него ещё не было, и
запускает его сам.

Первый прогон на сервере выполнен и замерен 25.09.2026: старт 08:12:21 UTC,
финиш 08:18:33, итого 371 с. Строка журнала — «Готово: 153 сохранено,
0 документов, 0 уже было от другого источника, 0 ошибок, 368.6 с». Обойдено три
профиля, новых закупок 130 из ЕИС и 42 со Сбербанк-АСТ, после дедупликации 153
уникальных; Контур.Закупки пропущен штатно — «последний платный поиск был 2,3 ч
назад, а интервал между прогонами — 6,0 ч». Один запрос к Сбербанк-АСТ вернулся
с HTTP 504, прогон продолжился и в итоговые ошибки не попал: ошибка источника по
одному ключевому слову не отменяет остальные.

Документов прогон сохранил ноль, и это не сбой: файлы догружаются по закупкам,
переведённым в «Интересное», а очередь анализа была пуста. Отдельное задание
`documents` на две закупки, поставленное через `POST /api/sync-jobs`, воркер
забрал через 8 с и выполнил за 7,8 с: 14 файлов (5 и 9), 6 пропущено как
форматы без разбора, AI-разбор не запускался.

Шесть минут — не обещание, а один замер при пустой очереди разбора. Прогон
ограничен изнутри, а не сетью: 25 минут на скачивание (`FETCH_BUDGET_MS`) и
20 минут на дренаж очереди разбора (`WORKER_BUDGET_MS`) в
`scripts/fetch-tender-documents.ts`, то есть дольше ~45 минут он не идёт.
Недоделанное остаётся в очереди и догоняется следующим прогоном.

Торопить не нужно: во время долгой работы воркер пишет пульс отдельным таймером
раз в 5 минут, поэтому панель не покажет «пропал» посреди прогона.

Успех выглядит так:

- в журнале есть строка «плановый прогон … запускаю scripts/sync-eis.ts» и
  итоговая строка «Готово: N сохранено, … , M ошибок, T с»;
- на `/admin/jobs` плитка «Прогон по расписанию» показывает свежий момент,
  «Выход в сеть» — российский адрес, подпись — «Сервер в России на связи N мин назад»;
- в ленте появились закупки. Документация у них возникает не сама: её приносит
  задание `documents` (платный поиск или купленная карточка) либо догрузка в
  конце самого прогона — по закупкам, переведённым в «Интересное». Поэтому
  «0 документов» в итоговой строке — норма для прогона, которому нечего
  догружать: в «Интересном» нет закупок без документации.

Если прогон прервался с кодом 2 и сообщением про адрес — выход зарубежный,
данные в базе не тронуты (скрипт проверяет связь до записи).

## Отключение задачи Windows

Делать **только после** первого успешного прогона на сервере. Две машины в одном
расписании — это двойной обход источников: лишняя нагрузка на ЕИС и повторная
запись одних и тех же строк. Платного ключа это не касается — момент последнего
поиска Контур.Закупок хранится в общей базе
(`konturCacheRepository.lastBillableCallAt`), поэтому вторая машина видит его и
пропускает Контур, если шести часов (`KONTUR_MIN_INTERVAL_HOURS`) ещё не прошло.

```cmd
schtasks /Change /TN "TenderFit EIS Sync" /DISABLE
```

Задачу именно отключают, а не удаляют: она — план отката.

## Обновление кода

```bash
TENDERFIT_VPS=root@<адрес> deploy/deploy-worker.sh --restart
```

Скрипт собирает архив дерева без `node_modules`, `.next`, `logs` и любых `.env*`
(и прерывается, если файл окружения всё-таки попал в архив), распаковывает
поверх кода и ставит зависимости **полным** `npm ci`: воркер запускается `tsx`,
а он лежит в `devDependencies`, поэтому `--omit=dev` оставил бы службу без
исполняемого файла.

`--restart` прерывает текущее действие воркера. Задание, оставленное в
`processing`, вернётся в очередь очисткой потерянных — не сразу, а когда от
`claimed_at` пройдёт порог `SYNC_STALE_JOB_MINUTES`. Скачанные наполовину файлы
придётся качать заново, поэтому перезапускать стоит, когда очередь пуста. Без
флага скрипт печатает команду перезапуска и оставляет решение человеку.

## Повседневное обслуживание

| Подпись на панели | Что это значит |
| --- | --- |
| Сервер в России на связи N мин назад | норма |
| Сервер в России не выходил на связь N мин | процесс остановлен или машина недоступна: `systemctl status`, `journalctl -u tenderfit-worker -n 100` |
| Сервер в России ещё не выходил на связь | служба ни разу не запускалась, или `SYNC_WORKER_ID` расходится с продом |
| Сервер выходит в сеть не из России | сменился адрес (переезд, VPN, NAT провайдера). Документация не загрузится, пока выход не станет российским |
| Отметка времени сервера не читается | часы на сервере сбиты или в базе не ISO-строка |

Полезные команды:

```bash
journalctl -u tenderfit-worker -f                       # журнал сейчас
journalctl -u tenderfit-worker --since "1 hour ago"     # что было за час
sudo systemctl restart tenderfit-worker                 # перезапуск
systemctl --no-pager -l status tenderfit-worker         # состояние службы
```

Порог «пропал» — 15 минут (`WORKER_STALE_AFTER_MIN`), порог потерянного
задания — 45 минут (`SYNC_STALE_JOB_MINUTES`). Тик последовательный: воркер
дожидается дочернего процесса, поэтому перехватить собственное задание не
может — порог касается только строк, оставленных убитым процессом. Ниже самого
долгого прогона (~45 минут, см. выше) его ставить нельзя: задание, которое ещё
качает файлы, вернулось бы в очередь и пошло заново.

Остановка по `systemctl stop` ждёт до 10 минут, пока воркер доделает текущее
действие. Нужен немедленный останов — `sudo systemctl kill -s SIGKILL
tenderfit-worker`; задание вернётся в очередь на следующем старте.

## Откат

```bash
sudo systemctl disable --now tenderfit-worker
schtasks /Change /TN "TenderFit EIS Sync" /ENABLE
```

Данные при этом не теряются: оба прогона пишут в одну базу, а ключ уникальности
закупки — реестровый номер, поэтому повторный обход создаёт обновления, а не
дубли. Плановые прогоны подхватывает вторая машина — задачу Windows только что
включили, поэтому лента пополняется по расписанию. Очередь заданий остаётся в
базе нетронутой, но разбирать её некому: кнопка «Найти новые закупки» продолжит
ставить прогон в очередь, а выполнит его и скачает документацию только
вернувшийся сервер.

## Безопасность

- ключи — только в `/etc/tenderfit/worker.env` с правами 640. Ни в дереве кода,
  ни в архиве деплоя, ни в переписке;
- ключей модели на сервере нет вовсе: глубокий разбор выполняет прод, а воркер
  лишь вызывает `${SYNC_BASE_URL}/api/analysis/worker`. Второй комплект
  `LLM_API_KEY` на арендуемой машине — лишний повод для утечки без пользы;
- `NODE_TLS_REJECT_UNAUTHORIZED=0` на сервере запрещён: переменная отключает
  проверку сертификатов для всех запросов процесса. Если провайдер подменяет
  сертификаты, добавьте его корневой сертификат в систему и укажите его через
  `NODE_EXTRA_CA_CERTS`;
- корень Минцифры берётся из `deploy/certs/russian_trusted_root_ca.pem`, и
  скрипт деплоя сверяет его отпечаток SHA-256 с зашитым значением до установки.
  Подмена корневого сертификата означает подмену всей цепочки доверия, поэтому
  проверка жёсткая: не совпало — деплой прерывается;
- на сервер заходят ключом (`TENDERFIT_SSH_KEY`, на рабочей машине —
  `~/.ssh/id_ed25519_tenderfit_vps`). Вход по паролю в `/etc/ssh/sshd_config`
  стоит закрыть: `PasswordAuthentication no`, затем `systemctl reload ssh`;
- юнит запускает воркер под отдельным пользователем с `ProtectSystem=strict` и
  правом записи только в `logs/` — там лежит замок `worker.lock` против второго
  воркера на той же очереди;
- панель `/admin/jobs` только читает очередь: кнопки поставить задание там нет,
  потому что ролевой модели в приложении нет и страница доступна любому вошедшему.

## Что осталось непроверенным

- хранилище ЕИС под большим объёмом. Прогон снял десятки страниц поиска и 14
  файлов; как оно ответит на сотни файлов подряд с одного дата-центрового адреса
  (троттлинг, блокировка диапазона), неизвестно. Признак проблемы — рост
  `недоступно` и `сбоев` в отчётах заданий при прежнем числе закупок;
- путь кнопки «Найти новые закупки» до очереди. Кнопка ставит `full_sync` с
  `reason: "press"` тем же роутом `POST /api/sync-jobs`, который проверен прямым
  запросом; живьём из браузера на проде её не нажимали, поэтому непроверенным
  остаётся состав тела запроса на клиенте (`syncJobApiService.enqueueFullSync`),
  а не воркер. Живой платный поиск с флагом `queueDocuments` в этой связке тоже
  не нажимали, чтобы не тратить запрос из суточных 30, — расхождение там возможно
  только в `queueDocumentsAfterSearch`;
- платный поиск Контур.Закупок с сервера: ключ принят и тариф прочитан, но в
  первом прогоне источник был пропущен по интервалу, то есть сам метод `search`
  с российского адреса ещё не вызывался;
- устойчивость службы на дистанции: перезапуски, замок `worker.lock`, рост
  `logs/` и потребление памяти за дни работы. Пик первой минуты — 139 МБ при
  4 ГБ на машине.

## Обход блокировок Vercel: свой домен через этот сервер (25.09.2026)

Российские провайдеры глушат часть anycast-адресов Vercel по IP (не по имени и
не по SNI): замер с машины пользователя показал, что `64.29.17.67` и
`216.198.79.67` роняют соединение даже с посторонним SNI, а `76.76.21.21`,
`64.29.17.195`, `216.198.79.195` отдают сайт за 0,1 с. DNS провайдера ротует
ответы между рабочими и глухими адресами, поэтому сайт то открывается, то
обрывается `ERR_CONNECTION_RESET` при полностью живом проде.

Два слоя обхода:

- **Заплатка на машине пользователя** — строка `76.76.21.21 tenderfit-ai-sage.vercel.app`
  в `C:\Windows\System32\drivers\etc\hosts` (скрипт `C:\Users\1\tf-tmp\pin-hosts.ps1`,
  только ASCII: Windows PowerShell 5.1 читает файл без BOM как cp1251 и кириллица
  ломает разбор). Лечит один компьютер и устаревает, если провайдер заглушит
  этот адрес.
- **Постоянный обход** — nginx на этом сервере принимает свой домен и проксирует
  на прод Vercel. Домен — `tender-fit.ru`, куплен 25.09.2026 на Бегете (там же
  аккаунт и оплата); `server_name` в конфиге уже `tender-fit.ru`, A-запись `@` →
  5.35.86.186 в зоне Бегета есть. Чужой tender-ai.tech не используется: он
  зарегистрирован в 2025 году в чужом аккаунте reg.ru, и на нём живёт референсный
  сервис TenderAI — тот самый пример витрины из docs. Конфиг
  `/etc/nginx/sites-available/tenderfit-proxy`: `proxy_pass` задан переменной с
  `resolver`, чтобы адрес Vercel пере-резолвился по TTL; `Host` и SNI выставлены
  в алиас `tenderfit-ai-sage.vercel.app`, потому что Vercel отвечает 404 на
  чужой `Host`; `client_max_body_size 64m` под загрузку документов;
  `proxy_read_timeout 300s` под кнопку поиска; отдельный `default_server`
  возвращает 444 любому чужому имени. Абсолютных редиректов от `Host` в
  приложении нет (middleware отсутствует, единственный redirect в
  `next.config.mjs` относительный), поэтому имя алиаса в браузер не протекает.

Чужое имя на адрес сервера обрывается соединением, то есть прокси не открытый.

Домен работает с 25.09.2026. Делегирование в файле зоны .ru появилось примерно
через полтора часа после покупки: до этого `a.dns.ripn.net` отвечал NXDOMAIN,
хотя whois уже показывал `REGISTERED, DELEGATED` — реестровая база опережает
файл зоны. Сторож на сервере дождался `status: NOERROR` с третьей попытки и сам
выпустил сертификат: Let's Encrypt, `CN=tender-fit.ru`, ECDSA, действует до
24.12.2026, `certbot.timer` включён и срабатывает дважды в сутки. `http://`
отдаёт 301 на `https://`, корень — 307 на `/dashboard`. Проверка снаружи без
всяких `--resolve`: `curl https://tender-fit.ru/dashboard` → 200 за 0,2 с;
в браузере панель открывается целиком, 40+ запросов и все 200.

Статика Next.js кэшируется на сервере (`location /_next/static/`, зона
`tfstatic` из `/etc/nginx/conf.d/tenderfit-cache.conf`, отклик несёт заголовок
`X-Cache`), поэтому одна страница больше не порождает несколько десятков
обращений к Vercel. HTML и API не кэшируются; файлы `/_next/static/*` адресованы
хэшем содержимого и устаревают только вместе со страницей, которая на них
ссылается. Заплатка в `hosts` на машине пользователя остаётся запасным путём
для старого алиаса.

**Vercel отвечает автоматической проверкой на всплеск запросов с одного адреса.**
Замер 25.09.2026: после серии частых обращений сервер получил `403` с
заголовком `x-vercel-mitigated: challenge` и страницей «Vercel Security
Checkpoint» — в браузере это «Не удалось проверить ваш браузер. Код 21», —
хотя машина пользователя в ту же минуту отвечала 200. Своих правил в Vercel
Firewall нет (`GET /v1/security/firewall/config` → `{"active":null,…}`), а обход
по IP дают только тарифы Pro и Enterprise (`GET /v1/security/firewall/bypass` →
`payment_required`). Прошло само за 2,5–3 минуты; обычное открытие страницы
проверку не вызвало. Вывод: не обстреливать прод циклами проверок, а увидев
«Код 21» — подождать пару минут и повторить.
