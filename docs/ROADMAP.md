# Дорожная карта

## Этап 1 — Подтверждение ценности (после MVP)

- Дать 5–10 целевым пользователям (ИП/малые компании) пройти онбординг и неделю пользоваться ежедневным отчётом.
- Метрики: доля вердиктов, отмеченных как полезные (FeedbackButtons); конверсия «рекомендовано → заявка подана»; время на разбор одной закупки.
- Калибровка весов скоринга по обратной связи (веса вынесены в `SCORE_WEIGHTS`, меняются без правки логики).

## Этап 2 — Реальные данные ЕИС

- Перенести `EisTenderSourceAdapter` (уже рабочий, см. ACCESS_EIS.md) на сервер: API-route или cron-импорт в БД.
- Дозагрузка карточки закупки для региона, документов и печатной формы (в фиде ЕИС регион отсутствует: заполнен для 3 из 116 живых закупок). Это единственный надёжный способ получить регион — угадывание по тексту даёт штаб-квартиру заказчика вместо места работ, замер и разбор в ACCESS_EIS.md, «Регион». Цена: один дополнительный запрос на закупку при ~2 запросах в секунду.
- Региональный фильтр по ЕИС: единственный найденный параметр `oktmoIds` (коды ОКТМО) географически точен, но для пяти субъектов из 85 возвращает ноль записей, поэтому в `buildEisSearchUrl` не внесён — нужен разбор семантики параметра, см. ACCESS_EIS.md, раздел «Регион». Сейчас `regions` в профилях синхронизации применяют все источники, кроме ЕИС; кто как — записано один раз в поле `honoursRegions` привязки источника (`src/services/tenderSourceRegistry.ts`), и перечисления площадок здесь намеренно нет: список менялся трижды за две недели. Большинство отбирает по каноническому наименованию на своей стороне, Фабрикант — по карточке на стороне адаптера; по ЕИС скрипт печатает предупреждение.
- Кэш и rate-limit (~3 req/s), retry на пустых ответах Varnish — уже заложены в адаптер.
- Хранилище: PostgreSQL (Supabase): таблицы tenders, documents, analyses, profiles; репозитории переключаются с localStorage на API без изменения UI.

## Этап 3 — Улучшение AI-анализа

- LLM-анализ уже работает (шлюз routerai.ru, Gemini 2.5 Flash; замер 2026-09-22 — ₽6,60 и 89 с на закупку с 328 тыс. знаков документации, ≈₽0,02 за 1000 знаков): извлечение требований, блокеров, рисков из документации. Пайплайн: загрузка документа → парсинг (PDF/DOCX/CSV) → промпт → валидация JSON-схемы → вердикт.
- Расширить `DocumentExtractor`: OCR для сканов PDF, извлечение таблиц и координат фрагментов.
- Обязательная Zod-валидация ответа LLM существующей схемой (AI_ANALYSIS_SCHEMA.md); fallback на детерминированный анализ при невалидном ответе — уже заложено.

## Этап 4 — Доставка и монетизация

- NotificationProvider: реальная отправка email (Resend/SES) и Telegram-бот (утренняя сводка + срочные алерты).
- Роли ADMIN/MANAGER/ANALYST/VIEWER, командные воркспейсы.
- Биллинг: подписка по числу профилей поиска и глубине анализа.

## Известные ограничения MVP (осознанные заглушки)

- Авторизация имитируется (localStorage), реальных сессий нет.
- Уведомления не отправляются — только формируются внутри приложения.
- Один сохранённый фильтр; профиль поиска применяется к фильтрам частично (ключевое слово + закон + регион + цена).
- Анализ детерминированный: keyword matching вместо семантики; синонимы работают только если внесены в профиль.
- Регионы в демо-базе захардкожены; в реальном фиде ЕИС требуют дозагрузки карточки. В синхронизации поле `regions` сужает выдачу всех источников, кроме ЕИС: кто как это делает, записано один раз в `honoursRegions` привязки источника (`src/services/tenderSourceRegistry.ts`) — перечисление площадок здесь устарело бы к следующему подключению. Площадки, принимающие регион в форме поиска, отбирают по каноническому наименованию на своей стороне; Фабрикант — по карточке на стороне адаптера. ЕИС региональный фильтр не поддерживает и собирает всю Россию (см. ACCESS_EIS.md).
- Документация коммерческих закупок Сбербанк-АСТ не читается: файлы лежат в карточке площадки за входом по КЭП, а поисковый API отдаёт только метаданные лота. `fetchDocuments` адаптера возвращает пустой список — причину показывает карточка закупки, а глубокий анализ по такому источнику не создаётся (`deepAnalysisBlocker`). Нужен либо парсер страницы PurchaseView со входом, либо агрегатор, отдающий файлы по договору; замер площадок — в REFERENCE_PLATFORM_PROBES.md.
- Документация Росэлторга не читается: ссылки в карточке ведут на отдельный хост `com.roseltorg.ru/file/get/…`, а его `robots.txt` запрещает доступ роботам целиком (`Disallow: /`, разрешена только главная); тот же путь на `www` отвечает 404. `fetchDocuments` возвращает пустой список без единого запроса, а причина записана в каталоге источников (`documentsReason`) и показывается карточкой закупки. Прирост источника не в файлах, а в процедурах с номерами площадки (`B`, `COM`, `ATOM`, `CORP`, `VTB`, `ROSSETI`), которых в реестре ЕИС нет вообще: из 60 проверенных зондом строк таких 44. Извещения 223-ФЗ остаются за ЕИС — приоритет Росэлторга ниже агрегаторов намеренно, чтобы бедная запись не затёрла полную. Замер — в REFERENCE_PLATFORM_PROBES.md, раздел «Третья волна».
- Фабрикант подключён 02.10.2026 по слову владельца («сделай фабрикант»): решение третьей волны отложено, адаптер построен и проверен живым прогоном — 96 уникальных закупок за 119,8 с по трём профилям. Запрос на каждую закупку (N+1) оказался не запретительным при бюджете задачи в 25 минут. Документация по-прежнему закрыта со всех четырёх сторон: `content.fabrikant.ru` — `Disallow: /` и `Crawl-delay: 3`; `www` запрещает `/files/`, `?action=download` и `?action=xml_export_auctions`; `api.` отвечает 403; у `44.` robots нет, но прямых ссылок на файлы в карточке тоже нет. Поэтому в каталоге источников у Фабриканта `documents: "none"` с причиной, а `fetchDocuments` возвращает пустой список.
- Фабрикант показывает анониму не всё. По части ключевых слов площадка вместо выдачи печатает «Доступ к просмотру процедуры ограничен … авторизуйтесь на ЭТП» с кодом HTTP 200 (замер 02.10.2026 на слове «МФУ»: 198 747 байт, три куска RSC-потока, ни одного `lotId`). Это третий исход поиска наряду с выдачей и честной пустотой «По вашему запросу ничего не найдено». Адаптер признаёт его ответом площадки и считает отдельным счётчиком, а журнал прогона печатает «не опрошено слов — доступ к просмотру процедуры ограничен (N)». Значит бесплатный анонимный поиск покрывает не всю площадку, а только открытую её часть, и сравнивать Фабрикант по полноте с ЕИС нельзя.
- Фабрикант не отдаёт регион в строке выдачи, а `customer_region_ids[]` фильтрует по региону заказчика, а не по месту поставки: закупка с поставкой в нужный субъект исчезла бы без следа. Регион применён по карточке на стороне адаптера (`honoursRegions: true`), а закупки, у которых регион не определён, считаются отдельной причиной и не пропадают молча.
- Фабрикант: строка выдачи ведёт не только на карточку `/v2`. Живой прогон отбрасывал строки, ведущие на «Маркет», в секцию Росатома и в секцию 44-ФЗ, а обход секций без ключевого слова показал ещё и 19 строк из 79, ведущих на `zakupki.gov.ru`. Причины разделены по виду адреса (`fabrikantCardUrlKind`), потому что строка в ЕИС — не потеря: то же извещение приносит адаптер реестра и приносит с документами. Открытый вопрос: открыть ли секцию Росатома отдельным парсером — 12 отброшенных строк в одном профиле говорят, что там есть объём.
- «Последний прогон» в ленте собирается только по платному источнику. Метку `synced_at` пишет одна ветка сохранения — для строк `data_source = 'KONTUR'` (`scripts/sync-eis.ts`), поэтому `selectLastKonturBatch` (`src/domain/lastSearch.ts`) нечем обобщить на бесплатный прогон: у строк остальных площадок метка пуста. Отсюда и подписи «Новые · платный поиск» вместо «новые после прогона». Чтобы блок работал для любого источника, метку нужно писать всем строкам прогона (момент начала прогона уже есть — `syncStartedAt`); до этого момента обобщение было бы неправдой.
- `src/components/dashboard/LastSearchCard.tsx` не импортируется ни одним экраном: карточку «Результат последнего поиска» заменил блок на экране «Сегодня» и ссылка «весь платный поиск (N)» в ленте. Решение не принято — либо вернуть карточку на экран «Закупки» (она показывает состав партии и причину отсева), либо удалить файл вместе с тестами. Оставлять надолго нельзя: компонент расходится с подписями, которые правятся в другом месте.
- РТС-тендер не подключён, и парсингом подключён не будет. Пятая волна зондов 03.10.2026 перебрала 42 имени зоны `rts-tender.ru` и нашла всё, что искала: публичную форму поиска (`www.rts-tender.ru/poisk`, на которую ссылается карточка Контур.Закупок и которая принимает номер извещения параметром), карточку торга на поддомене заказчика и файл-хост `market-api.rts-tender.ru`. Закрыты все три: первые два — стеной Anti-DDoS с JS-челленджем (HTTP 503 и 33–42 КБ страницы на каждом пути, включая `robots.txt`), третий — отказом приложения (403 на `/` и `/files/`). Стену не проходили по двум независимым основаниям: куку выдаёт скрипт площадки, а недоступный `robots.txt` по RFC 9309 означает, что запрещённым считается всё. Записи `RTS_TENDER` в каталоге источников нет намеренно: адаптеру нечего опрашивать, а заглушка пообещала бы пользователю источник, который никогда не ответит. Регулируемые торги площадки (44-ФЗ, 223-ФЗ, ПП РФ 615) не теряются — они публикуются в ЕИС и берутся оттуда, в том числе по конкретному заказчику через `customerInns`; теряются только чисто коммерческие и корпоративные процедуры. Вернёмся при одном из двух условий: стена исчезнет или появится API-хост с разрешающим `robots.txt` (прецедент — экспортный API ТЭК-Торга), либо появится договор или аккредитация с правом входа через SSO и скачивания файлов с `market-api`. Замер — в REFERENCE_PLATFORM_PROBES.md, раздел «Пятая волна: РТС-тендер», и в REFERENCE_RTS_TENDER.md.
- Деплой приложения не переживает обрыв SSH. `deploy/deploy-app.sh` ставит зависимости, собирает Next.js и перезапускает службу в одной удалённой сессии: когда соединение рвётся, службы не страдают, но деплой останавливается наполовину — дерево кода уже новое, а сборка и перезапуск не выполнены, и сайт продолжает отдавать прежнюю версию. 03.10.2026 так и вышло (`Connection reset by peer` во время `npm ci`), остаток пришлось доделывать вручную: `setsid nohup … npm run build` и `systemctl restart tenderfit-app`. В оба деплой-скрипта добавлен keepalive (`ServerAliveInterval=15`), он убирает самую вероятную причину — молчаливое соединение, пока `npm ci` пишет stderr в файл. Полное решение: запускать удалённую часть detached и опрашивать журнал короткими подключениями — тогда обрыв не прерывает деплой вовсе.
