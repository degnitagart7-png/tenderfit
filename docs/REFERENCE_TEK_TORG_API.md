# ТЭК-Торг: публичный экспортный API процедур

> Осмотр 01.10.2026 с российского сервера 5.35.86.186, только чтение. Источник фактов —
> `https://api.tektorg.ru/` (корень отдаёт JSON-оглавление), `https://api.tektorg.ru/procedures`
> (описание параметров), `https://api.tektorg.ru/procedures/wsdl` (схема, 12 377 байт),
> справочники `/lists/sections`, `/lists/types` и восемь живых вызовов SOAP. Первый вызов
> сорвался на регламентных работах (500/502, площадка назначила окончание на 01:30 МСК
> 02.10.2026); вечером того же дня API поднялся, и всё ниже написанное — результаты
> настоящих ответов, а не чтение схемы.
>
> Почему это важно: единственная из одиннадцати зондированных площадок, которая сама
> публикует интерфейс для выгрузки процедур **вместе с документами** — и отдаёт байты
> файлов без ключа. Остальные отдают файлы только через хост, закрытый в `robots.txt`
> (см. `REFERENCE_PLATFORM_PROBES.md`).

## Корень API

`GET https://api.tektorg.ru/` → `application/json`, без авторизации:

```json
{ "resources": [
    { "url": "http://api.tektorg.ru/lists",      "description": "Публичный раздел справочников." },
    { "url": "http://api.tektorg.ru/procedures", "description": "Публичный раздел экспорта процедур." }
] }
```

Единственная операция — SOAP `procedures`, точка `https://api.tektorg.ru/procedures/soap`,
`soapAction="urn:procedures"`, `style="rpc"`, namespace `https://api.tektorg.ru/procedures/soap`.
В WSDL нет ни одного упоминания авторизации: слов `auth`, `token`, `key`, `login`,
`password`, `security`, `signature` — ноль. Ключа не просит и оглавление.

`api.tektorg.ru/robots.txt` отвечает `User-agent: * / Disallow: /`. Это запрет индексации
для поисковиков на хосте, который сам называет свои разделы публичными и сам отдаёт
оглавление любому GET-у; к вызову заявленного интерфейса он отношения не имеет. Для
сравнения: файловый хост ГПБ `com.etpgpb.ru` закрыт так же, но ничего публичного не
публикует, и там этот запрет — про файлы лота.

## Параметры запроса `exportRequestType`

| Параметр | Тип | Что делает |
| --- | --- | --- |
| `startDate` / `endDate` | dateTime | окно по дате публикации |
| `startUpdateAt` / `endUpdateAt` | dateTime | окно по дате обновления — готовый инкрементальный синк |
| `sectionCode` | string | алиас секции, словарь `/lists/sections` |
| `registryNumber` | string | номер закупки на площадке |
| `eisRegistryNumber` | string | номер в ЕИС |
| `typeId` | int | тип процедуры, словарь `/lists/types` |
| `organizerINN` / `customerINN` | string | ИНН организатора / заказчика |
| `limitPage` / `page` | int | постраничная раздача |
| `sort` | sortRules | правила сортировки |

Все параметры `minOccurs="0"` — запрос валиден и пустым.

Ответ: `totalProcedures`, `currentPage`, `totalPage`, `limitProceduresInPage`,
`sectionName`, `sectionCode`, `procedures` (список).

`city`, `street`, `house`, `countryIsoNr`).

Документ (`documentType`, встречается и у процедуры, и у каждого лота):

```xml
<xsd:complexType name="documentType">
  <xsd:sequence>
    <xsd:element name="id" type="xsd:int" minOccurs="1"/>
    <xsd:element name="filename" type="xsd:string" minOccurs="1"/>
    <xsd:choice>
      <xsd:element name="removed" type="xsd:boolean"/>
      <xsd:element name="file" type="xsd:string"/>
    </xsd:choice>
  </xsd:sequence>
</xsd:complexType>
```

`choice` между `removed` и `file` — это ровно то, чего нам не хватало в ЕИС: явный сигнал
«документ отозван», а не молчаливое исчезновение. В живом ответе за 01.10.2026 `removed`
не встретился ни разу, а `file` — всегда абсолютный HTTPS-адрес (раздел «Документы» ниже).

`startUpdateAt`/`endUpdateAt` ложатся в `checkChanges` напрямую и проверены живым вызовом:
окно обновления за сутки даёт 207 процедур против 73 опубликованных, и среди них — закупки
от 23–24.09, у которых изменилось только состояние (см. «Инкрементальный синк работает»).

## Живой вызов: что проверено 01.10.2026

Тринадцать запросов с российского сервера за один день, только чтение: пустой, по всей
секции, по суткам, с `limitPage` 5, 100 и 500, с окном обновления, HEAD и ranged GET на
документ. Ни одной 429, ни одной капчи, ни одного требования ключа. Время ответа от 0,5 до
26,2 с — медленно отвечает первый запрос, дальше площадка разогревается; для ночного синка
это несущественно.

**1. Конверт.** Принимается вариант с именем части из WSDL, `style="rpc"` + `use="encoded"`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
                  xmlns:tns="https://api.tektorg.ru/procedures/soap"
                  soapenv:encodingStyle="http://schemas.xmlsoap.org/soap/encoding/">
  <soapenv:Body>
    <tns:procedures>
      <symbol>
        <sectionCode>zakupki</sectionCode>
        <startDate>2026-10-01T00:00:00+03:00</startDate>
        <endDate>2026-10-01T23:59:59+03:00</endDate>
        <limitPage>100</limitPage>
        <page>1</page>
      </symbol>
    </tns:procedures>
  </soapenv:Body>
</soapenv:Envelope>
```

POST на `https://api.tektorg.ru/procedures/soap`, заголовки `Content-Type: text/xml;
charset=utf-8` и `SOAPAction: urn:procedures`. Ответ приходит с `Content-Type: text/html` —
это особенность площадки, а не ошибка: тело начинается с `SOAP-ENV:Envelope` и не содержит
`Fault`. Определять успех по заголовку здесь нельзя, только по телу.

**2. Ключ не нужен.** Пустой запрос (все параметры `minOccurs="0"`) возвращает данные:
`sectionCode` по умолчанию — `44fz`, `totalProcedures` — 886 791. Никакой авторизации.

**3. `file` — это адрес, а не base64.** `https://api.tektorg.ru/open-api/documents/procedure/{id}`,
тоже без ключа. HEAD отдаёт `200`, `Content-Type: application/msword`, `Content-Length: 44544`,
`Accept-Ranges: bytes` и `content-disposition` с обоими вариантами имени — ASCII-транслитом
и настоящим через `filename*=utf-8''…`. Ranged GET на первые 64 байта отвечает `206 Partial
Content` с `Content-Range: bytes 0-63/44544`, и байты начинаются с `D0 CF 11 E0` — это
настоящий OLE2-контейнер `.doc`, а не страница ошибки.

Отсюда три практических вывода. Байт идёт в существующий `attachmentParser` напрямую,
загрузчик не нужен. Имя файла берём из `filename*`, а не из `<filename>` ответа: в ответе
оно в той же кодировке, что и весь XML, а в заголовке продублировано правильно. `Accept-Ranges`
означает, что большие файлы можно докачивать и забирать параллельно.

**4. Объём и постраничность.** Во всей секции `zakupki` — 136 254 процедуры. За сутки
01.10.2026 — 73, и `limitPage=100` вернул все 73 одной страницей (`totalPage=1`, 489 264 байт).
Из этих 73 у 47 заполнен `eisRegistryNumber` — они пересекаются с ЕИС, которую мы и так
читаем бесплатно; **26 без номера ЕИС — чисто коммерческие закупки, которых в ЕИС нет**,
и именно за ними стоит идти на площадку.

Из того же ответа: 202 документа (196 на уровне процедуры, 6 на уровне лота), от 1 до 11
на процедуру, без документов не осталось ни одной; 74 лота; `datePublished` от 07:02:08 до
21:03:19 +03:00, то есть на момент вызова самым свежим данным было 8 минут; 41 различный ИНН
по организаторам и заказчикам; валюта у всех 73 — RUB; 8 различных `procedureType`.

**5. Цена и предмет заполнены не везде.** `startPrice` есть у 58 лотов из 74, пустых и
нулевых среди них нет, `startPriceUndefined` не встретился ни разу — то есть площадка
просто не присылает элемент, а не помечает цену как неопределённую. Значения целые
(`376200`, `4485386`), а рядом `startPriceNoNds` с копейками (`1220370.49`), отношение
1,0 или 1,22 — оба поля в рублях, цена без НДС выводится, но брать надо `startPrice`.
Непустой `subject` — у 66 лотов из 74. Вывод для интерфейса: пометка «цена не указана»
(задача #98) здесь понадобится, и у восьми лотов из семидесяти четырёх не будет ни цены,
ни предмета — их надо показывать с причиной, а не отбрасывать.

## Инкрементальный синк работает

`startUpdateAt`/`endUpdateAt` — это настоящая дельта, а не переименованный фильтр по дате
публикации. Окно обновления за 01.10.2026 по секции `zakupki` вернуло **207 процедур** —
втрое больше, чем опубликовано за те же сутки (73). Разница и есть изменения в уже идущих
закупках: на странице 20 лежат процедуры, опубликованные 23–24.09.2026, у которых
`dateUpdated` стоит 01.10.2026 (06:51, 09:50, 10:31, 15:12, 15:30). Недельное окно
25.09–01.10 даёт 982 процедуры.

Это ровно то, что нужно `checkChanges`: разъяснения, продление срока, публикация протокола —
всё приходит одним запросом, и не надо перебирать 136 тысяч процедур, чтобы узнать, что
изменилось. Суточная дельта помещается в одну страницу.

**Потолок страницы — как минимум 500.** `limitPage=500` принят: 500 процедур одним ответом,
4 734 822 байта, 20,3 с, без `Fault`. Значит полный перебор секции — 273 страницы, порядка
полутора часов, а не восемь часов при `limitPage=100`. Одна процедура весит примерно 9,5 КБ,
суточная дельта — около 2 МБ.

Пагинация честная: `totalPage` = ⌈`totalProcedures` / `limitPage`⌉ (207 при `limitPage=1`,
42 при `limitPage=5`, 2 при `limitPage=500` для 982), `currentPage` и
`limitProceduresInPage` возвращаются как запрошены.

## Сухой прогон по профилям: 02.10.2026

```
npx tsx scripts/sync-eis.ts --dry-run --sources=TEK_TORG --limit=50
```

«Проверка связи · ТЭК-Торг: доступен (HTTP 200)», в окне публикации 75 процедур, по трём
боевым профилям отобрано **7 уникальных** закупок: «Автомобили» — 6, «Компьютеры и
оргтехника» — 0, «Строительство и ремонт» — 1. Прогон занял 3,9–4,4 с вместе с проверкой
связи, в базу не записано ничего.

Отсев напечатан с причиной, а не молча: у автомобильного профиля «отброшено — ключевое

по цене — это лимит профиля, а не потеря данных: ТЭК-Торг публикует много запросов цен
без НМЦК, и нуль в `price` означает «не опубликована» (см. `TenderFinancialTerms`).

Платных запросов прогон не делает: Контур.Закупки при `--sources=TEK_TORG` не опрашивается
вовсе, и журнал расхода тарифа не меняется.

## Документы площадки: живая загрузка 02.10.2026

Путь «экспорт процедур → список документов → байты → текст» проверен целиком, три прогона
с российского хоста, все три завершились без ошибки. Писалось в память, а не в базу:
миграция `TEK_TORG` на тот момент ещё не была применена.

`ЗП610102` — два документа, 44 380 байт, 17 945 знаков текста, 0,7 с на всё.
`ЗП6082206` — три документа: извещение и два архива лотов. При бюджете 30 000 знаков
извещение обрезалось по бюджету, а оба архива получили причину «не влез в бюджет» **без
единого скачивания** — проверка формата и остатка бюджета стоит до загрузки байт, и это
видно по счётчику запросов, а не по комментарию в коде. При бюджете 400 000 знаков
разобраны все три: 91 700 + 83 703 + 86 866 = 262 269 знаков, ни одного пропуска, 2,6 с.
Архивы распаковываются тем же кодом, что и вложения ЕИС.

Двести шестьдесят две тысячи знаков — четверть потолка на закупку (1 000 000), то есть
типичная процедура площадки помещается в бюджет с запасом, и обрезается только извещение
у процедур с очень большим томом документации.

Отдельно: `api.tektorg.ru` не требует обхода проверки сертификата. Все запросы прошли с
обычным доверием к корневым сертификатам, в отличие от `zakupki.gov.ru`, где нужен корень
Минцифры. На сервере в России это означает, что для ТЭК-Торга не надо ни
`NODE_TLS_REJECT_UNAUTHORIZED=0`, ни `NODE_EXTRA_CA_CERTS`.

Не проверено живьём: документ, снятый с публикации (`<removed>`). В выдаче за сутки
такого не встретилось, поэтому ветка «адреса нет, файл отозван» покрыта только тестом на
фикстуре. Проверить её стоит на первой же процедуре, где экспорт пришлёт `removed`.

## Регион: 02.10.2026, треть выдачи получала Москву впустую

Проверка на живой выдаче за сутки (75 процедур) вскрыла не особенность площадки, а ошибку
нашего маппера. Поле `<region>` у процедуры заполнено редко, место поставки лота в половине
случаев стоит заглушкой «В соответствии с документацией о закупке» или «В соответствии с ТЗ»,
и регион тогда находился из адреса организатора. Головной офис заказчика — не место работ:
из 75 процедур **27 (36 %) получили «Москва»**, и как минимум 8 из них — ложные.

Эти восемь видны сразу, потому что субъект назван в самом названии процедуры: «Оказание услуг
автотранспортными средствами **на о. Сахалин**», «перевозка элементов строительных лесов
**в г. Рязань**», обслуживание и кузовной ремонт в Башкортостане, медицинские осмотры в
Тюменской области, заправка картриджей в Самарской области. У всех восьми адрес поставки —
заглушка, `<region>` пуст, а в карточку легла бы Москва. Для партнёра это двойной вред:
москвич видит работу на Сахалине, а сахалинец — не видит своей.

Решение: название процедуры и предметы лотов добавлены в список признаков региона **после**
места поставки и поля `<region>`, но **до** адреса организатора. То есть название работает
только там, где площадка не дала ни места поставки, ни региона. После правки тот же прогон
дал: расхождений названия и региона **ноль** (было восемь), Москва — **19 из 75** вместо 27,
сахалинская закупка `32616428629` показывает «Сахалинская область» и на уровне закупки, и
на уровне лота.

Что осталось нерешённым и чего не надо выдавать за решённое: словарь
`regionFromAddresses` знает субъекты, но не города. Название «в г. Ангарск» региона не даёт
(Ангарск — Иркутская область), и такая закупка по-прежнему уедет в адрес организатора.
Из 75 процедур название называло субъект у 16; у остальных 59 региона в названии нет вовсе,
и для них источник признака один — адрес организатора. Лечится это либо словарём городов,
либо местом поставки из документации, и то и другое — отдельная работа.

## Чего проверить не удалось

Лимит частоты площадка не объявляет, и тринадцать запросов за день его не нащупали: ни одной
429, ни одной капчи, время ответа 0,5–26,2 с. Настоящая проверка — боевой синк; начинать
стоит с паузы между страницами и следить за временем ответа, его рост — ранний признак
троттлинга.

Ответ приходит медленно и неравномерно (7–26 с на запрос), поэтому синк надо считать в
секундах на страницу, а не в запросах в секунду: 273 страницы полного перебора — это
полтора часа последовательной работы. Для ночного окна нормально, для «найти закупки по
кнопке» — нет, там остаётся ЕИС и Контур.

Не проверено, что площадка делает с дельтой за длинное окно: если `startUpdateAt` отодвинуть
на месяц, ответ может вырасти до десятков тысяч процедур и упереться в таймаут. Перед
реализацией стоит один раз спросить месяц с `limitPage=1` и посмотреть `totalProcedures`.

## Запасные пути, которые не годятся

SSR-страница `https://www.tektorg.ru/vitrina/procedures` отдаёт в `__NEXT_DATA__` живые
15 лотов из 90 958 (`listingLots.data`, страницы по 15, `totalPages` 6064) без всякого API.
Но это секция `sale`/`vitrine` — продажа имущества, а не закупки, и ссылки лотов ведут на
`sale.tektorg.ru/#com/procedure/view/…` c hash-маршрутом. Как запасной путь не годится,
как источник — тем более.

Список на `https://www.tektorg.ru/procedures` роботом не читается: SSR-оболочка
429 КБ приносит только словарь фильтров (`advancedSearch`: 41 тип, 5 статусов,
20 организаторов, регионы, ОКПД, ОКВЭД, ОКРБ, 38 секций), а `listingProcedures.data`
в ней пустой со `status: "loading"` — список догружается клиентским запросом к
`https://www.tektorg.ru/api-back` со статическим токеном из JS-бандла. Корень `api-back`
без токена отдаёт 302 на `/login`. Это внутренний интерфейс сайта, а не публичный, и
трогать его не надо: рядом лежит официальный экспортный API.
